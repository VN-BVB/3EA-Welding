# 3EA-Welding
3 External Axes Welding System
◮◮◮ 注意:
1. 项目仅限MSVC2017，C++11;
2. 除3rdParty.pri中涉及的库以外, 还需要在visual studio中安装MFC, 并正确配置相关环境;

◮◮◮ 多人协作代码准则:
1. 作为项目仓库的建立者, 应保证每个人在参与项目时免受骚扰. 构建包容的环境对于促进人工智能和计算机视觉等领域的创新至关重要.
   
2. 在您书写代码时, 请确保函数、变量、类名、注释等都能清晰地表达您的意图, 并避免使用不明确或可能引起误解的词语. 我们期待您的代码能够被其他开发者理解, 并能在不产生混淆的情况下被正确使用.
   
3. 命名准则: 我们强烈建议您的函数名使用小驼峰命名法, 例如void initStructLightCamera(), 变量名也使用小驼峰命名法, 例如structLightCamera, 类名使用大驼峰命名法, 例如RailWeldingSystem, 枚举、预编译宏以及常亮使用下划线全大写命名法, 例如enum WELD_TYPE { BACK_CORNER_BUTT, FRONT_CORNER_BUTT, BACK_BEAM_BUTT, FRONT_BEAM_BUTT, FRONT_HORIZONTAL_FILLET, FRONT_VERTICAL_FILLET }, 函数尽可能使用动词开头. 注释使用中文, 并在必要时使用英文.
   
4. 信号和槽的使用: 我们建议您的信号尽可能使用send作为开头, 槽尽可能使用when作为开头. 除非信号和槽中的参数只是简单的类型, 例如int, double, bool等, 否则请使用智能指针传递. 由于cv::Mat和pcl::PointCloud内部实现了引用计数, 因此不需要使用智能指针传递.
   
5. 模块搭建: 每一个功能模块都应当尽可能独立, 并在./src文件夹中独占一个子文件夹, 使用一个pri文件管理该模块. 在代码层面上, 除UI模块以外, 其余各功能模块原则上都需要独占一个子线程, 并务必不要使用继承QThread的方式实现, 而是使用继承QObject并moveToThread的方式实现. 在构建模块以及创建新类时, 应当充分考虑C++面向对象的特性, 不应再代码层面打破面向对象的设计原则. 例如, 结构光传感器中(如)有主副两个相机, 那么在代码层面就应当有两个对象, 而不是一个对象中包含两个相机. 这样做的好处是, 可以让代码更加清晰, 易于维护, 并减少错误的发生, 并提高代码的复用性和灵活性.
   
6. 单一职责: 我们建议您的函数、类、变量等尽可能只负责一件事情, 例如相机类只负责采集图像, 不负责处理图像, 图像的处理在对应的功能模块中进行. 同理, UI类以及各个UI模块类只负责『显示信息』和『响应交互』, 不负责处理信息和处理项目模块之间的逻辑交互关系, 处理信息请在各个子模块中进行, 各模块之间的逻辑交互请在RailWeldingSystem类中进行. 这样可以使代码更加清晰, 易于维护, 并减少错误的发生.
   
7. 子线程创建: 对于已经是独立模块的子线程模块来说, 我们建议您在其中继续创建子线程时遵循以下原则:
   1. 该模块中需要进行计算密集型的操作, 例如点云的处理等, 必要时请使用src/utils/common/ThreadPool中的线程池类进行管理;
   2. 该模块中的各个子模块需要同时工作, 例如结构光相机模块中的投影仪模块和相机模块;
   3. 如果该模块中的各个子模块工作是串行的, 例如分割方法定位焊缝模块中的图像分割子模块, 其它操作必须等待图像分割完成后才能继续进行, 此时不建议为图像分割单独创建一个子线程, 而是在图像分割子模块中进行操作, 以确保代码更加清晰简洁, 易于维护;
8. 请使用.gitignore来管理项目中的编译文件, 例如Makefile、Makefile.Release、Makefile.Debug、/build/、/debug/、/release/、/.qtc_clangd/等文件.
9. 在您的代码中, 请确保您的行为符合上述准则. 我们期待您的合作, 并欢迎您的贡献.
10. 如果您发现任何不符合上述准则的行为, 请及时向项目维护者报告，维护无果请直接与王教授反应，情形严重者将不参与项目的开发和维护.
